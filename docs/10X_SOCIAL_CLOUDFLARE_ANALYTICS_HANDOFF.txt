3. COLLECTION FINDINGS

The served collector constructs these categories, where supported:
  - Current page and referrer origin/path, navigation type, event type, timestamp,
    script versions and the site's public identifier. SPA mode is enabled and
    the script observes supported navigation/history APIs.
  - A random pageloadId, regenerated for supported route changes. It is not the
    client's persistent device ID or a Farcaster FID, but it is an identifier.
  - DNS/connection/TLS/request/response/DOM/load/paint measurements, protocol,
    transfer/body sizes and available JavaScript heap statistics.
  - Core Web Vitals: FCP, LCP, CLS, TTFB and INP. Diagnostics can include CSS
    selectors, layout rectangles, interaction type, LCP resource URL/size and
    timing breakdowns. The selector generator uses element IDs/classes.
  - Browser/engine versions derived from user-agent information; supported
    browsers may provide an OS platform version through client hints.

Cloudflare also documents dashboard dimensions such as country, device class,
browser and OS. These are provider-documented capabilities; this review did not
inspect this account's dashboard records or verify every dimension's values.
Source: https://developers.cloudflare.com/web-analytics/data-metrics/dimensions/

URL distinction: the current collector removes credentials, query strings and
fragments from its page-location and referrer fields. However, its LCP resource
URL bypasses that cleanup. A synthetic LCP URL containing ?review=synthetic and
#fragment survived unchanged in the constructed payload. This establishes a
collector path, not that any real secret was transmitted. Do not promise that
all URLs are query-free or that identifiers can never appear in diagnostics.
Paths may themselves identify profiles/casts. Keep credentials/private text
out of resource URLs and DOM IDs/classes; inspect actual authenticated payloads.

With the observed config, the code targets same-origin POST /cdn-cgi/rum (an
empty trailing query is possible). Initial-load data uses XHR; hidden-page
vitals use sendBeacon where available, with fallback support. This endpoint is
independent of the Farcaster /~api relay. No blanket API-body, message-text,
form-value, session replay or FID collection was found in this collector's
payload construction. That finding is limited to this script and does not
exclude information embedded in URLs/selectors or other providers' processing.

No cookie/localStorage/sessionStorage/IndexedDB API access was found in the
served script; the exercised paths also passed with storage access prohibited.
This does not mean a same-origin HTTP request cannot carry existing cookies
automatically, or that the rest of Social uses no persistent storage.

Cloudflare states its RUM beacon does not use browser storage and does not
fingerprint users. It says source IP addresses necessarily arrive with HTTP
requests but are discarded at the receiving edge for RUM, rather than stored
in RUM's core databases/logs. Processing can occur outside the visitor's country.
Do not extend those product-specific statements to CDN/security/API logs.
Sources:
  https://developers.cloudflare.com/speed/observatory/rum-beacon/
  https://developers.cloudflare.com/web-analytics/data-metrics/core-web-vitals/

Cloudflare's FAQ says query strings are not logged for Web Analytics. Distinguish
that provider statement about logging from the client LCP URL path above; it
does not prove every outbound field is redacted. The FAQ describes seven days
of unsampled data, longer-term aggregation/sampling and six months of accessible
analytics. Six-month dashboard access is NOT proof of deletion of every record
or backup. Account exports, retention controls and other logs were not verified.
Source: https://developers.cloudflare.com/web-analytics/faq/

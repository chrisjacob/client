2. TECHNICAL FINDINGS FROM FC CLIENT

These findings were established by source review on 21 October 2026. They describe code and defaults, not a complete production traffic capture or audit of hosting dashboards.

A. Requests and hosting
The production API base defaults to a same-origin /~api relay. A Cloudflare Pages Function forwards requests to https://farcaster.xyz/~api. A build-time setting can select a different API base, so confirm the actual deployed configuration.

The relay passes through request bodies and authorization/device headers while removing selected cookies and forwarding headers. It sets Cache-Control: no-store on relayed responses. That cache header is not proof that Cloudflare, upstream services, security tooling, or diagnostic systems retain no logs. Requests can include private account data and authentication information; data categories depend on the endpoint. A separate upstream websocket URL is also configured.

Therefore: disclose Code Hunt's infrastructure processing as well as upstream processing. Do not claim that every request travels directly from the browser to Farcaster, that 10X never handles authentication information, or that all service traffic goes through the relay.

B. Authentication and browser storage
The client has email magic-link login and a mobile/QR synchronization flow. The email form sends the supplied address through the configured Farcaster API client. Do not assume the Resend provider used elsewhere by 10X sends these upstream login emails.

Authentication tokens and onboarding state are persisted through localforage. Other preferences and a stable per-browser device identifier use localStorage; the device identifier is sent to the upstream API. The client also has query-cache persistence support. Storage technology and retention depend on the browser and application settings.

Authentication/session credentials are different from wallet seed phrases, wallet private keys, and protocol signing permissions. Logging in may establish an ongoing session capable of performing supported account actions. It is inaccurate to imply that each cast or other ordinary authenticated action requires a fresh approval in the mobile app. The exact granted permissions and revocation procedures need verification for each supported login flow.

C. Analytics: current code differs from a recommendation
The app initializes PostHog at startup. Its analytics configuration imports upstream development/production project settings and uses https://ph.neynar.com. The wrapper configures localStorage persistence, disables autocapture and automatic pageview capture, enables page-leave capture, and supports explicit events, user identification, and account-related properties. Some events are emitted before authentication.

Do not publish claims that analytics are disabled, anonymous-only, limited to essential storage, or sent only to Code Hunt based on this review. The recommendation is to disable inherited upstream analytics unless intentionally retained, then document the actual chosen behavior and any required controls. No analytics change has been implemented by this legal review. The API agent must flag that dependency to the FC Client agent/user rather than describe the recommended future configuration as an accomplished fact.

D. Third-party functionality
The client can host third-party Mini Apps and load external media/services. It also contains a feature-flagged KLIPY media picker. Opening or interacting with these features may create additional direct requests or share context with independent providers. Confirm what is enabled and what data is provided; do not list every 10X.MEME integration as if every Social user necessarily uses it.

E. Account/deletion wording currently needs correction in FC Client
The white-label deletion page currently claims that 10X stores no account information and describes an upstream email-based deletion process with a typical one-week completion time. These assertions were not substantiated by the review. They must not be carried into the shared policy. Upstream contact details, procedures, and timeframes require current verification.

Subsequent client cleanup removed the zero-storage claim and guaranteed deletion outcome/timeframe, and aligned the Support page with the privacy summary. The inherited upstream deletion contact remains subject to the verification noted above. The shared-policy work should still distinguish these different requests and responsibilities.

3. EXPLAIN THE DIFFERENT SYSTEMS IN PLAIN LANGUAGE

Use a short architecture/roles explanation covering:

* Code Hunt / 10X.Social: operates the branded interface and its infrastructure; processes relevant requests, local sessions/settings, and whichever diagnostics/analytics are actually enabled.
* Farcaster application services: upstream authentication, account, API, and application-specific services used by the client, operated by their respective provider(s) under applicable third-party policies.
* Farcaster protocol: the shared public social-data network. Public casts, reactions, and other supported public social records can be distributed to independent clients, nodes, and indexers. Snapchain is part of Farcaster's social-data infrastructure.
* Public blockchain networks: relevant identity/authorization registry events and wallet transactions, with their own public-record and permanence characteristics.

These are different data flows, not four sequential storage copies of every item. Do not classify email addresses, login tokens, private messages, public casts, and blockchain transactions as having the same visibility or storage. Public social data should not all be described as an immutable Ethereum transaction. Do not promise end-to-end encryption or specific private-message storage locations without evidence.
